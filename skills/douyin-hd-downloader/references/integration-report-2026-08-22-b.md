# 零 bit_rate 档形态：间歇失败与水印护栏（2026-08-22，3 条视频）

测试输入：`https://v.douyin.com/JGdjtlT0UuI/`（短链，`aweme_id=7675186991521068219`）

这条 case 与 [第一份报告](integration-report-2026-08-22.md) 的形态**完全不同**，而首版正是在这条路径上不可靠：

| | 第一份报告 | 本报告 |
|---|---|---|
| `video.bit_rate[]` | 12 档 | **0 档** |
| provider | `douyin_browser` | `iesdouyin_ssr`（不需要浏览器） |
| 唯一转码回退 | 无水印 1080p | **带水印 playwm** |

## 修复前：同一条链接，5 次跑出 3 种结果

| run | 结果 |
|---|---|
| 1、3、4 | ✅ original 43.5 MiB |
| 2 | ❌ 退出：`WAF challenge` |
| 5 | ⚠️ original `FAIL:ConnectTimeout` → 静默降级到 2.8 MiB 水印档，exit 0 |

三个根因，都经实测证实（非阅读推测）：

1. **`verifyCenter` 误报成 WAF**。抓 6 次页面对比：该字符串在 **6/6** 页面都出现，包括 5 次成功解析的页面。它是常驻 JS SDK 名，不是风控标记。误报把排查方向引向 cookie / 代理，而真实需求只是重试。
2. **完全没有重试**。SSR 单次成功率 4/6；但 ≤3 次独立尝试成功率 **6/6**（实测每次尝试所需次数：`[2,1,1,1,1,2]`）。
3. **一次 ConnectTimeout 就判原片无效**。10.4s 超时后，紧接着重探同一 URL 两次均为 206 / 45,562,198 bytes。43.5 MiB 原片被换成 2.8 MiB 水印视频，且 exit code 0、不报错。

## 加了重试还不够：连接超时的真实成因

「重试 3 次」的第一版修复**仍然会失败**——实测出现过**连续 3 次** ConnectTimeout，失败不是独立均匀分布的。

排查过程（两个假设都被实测证伪，记录如下以免后人重走）：

- ❌ *假设「某些 CDN IP 挂了」* → `www.douyin.com` 解析到 18 个 IP，**18/18 TCP 连接全部 0.0s 成功**。不是死 IP。
- ❌ *假设「触发了限流」* → 暂停 20s 后立刻重试**仍然失败**，且失败率与请求节奏无关。不是限流。
- ✅ **真实成因**：到部分边缘节点的路由不稳定，单次成功率约 50%、相互独立。关键观测是**健康连接 ~0.3s，坏连接固定挂满 10.2s**——而客户端 connect 超时上限恰好设成了 10s，于是**一个坏边缘就能吃掉整个重试预算**。

修法不是无脑加重试次数，而是**把 connect 超时压到 3.5s + 提高尝试次数**（`CONNECT_TIMEOUT_SECONDS = 3.5`，probe attempts 6）：坏边缘快速失败、立刻换一个。验证 5/5 成功，最坏 4.3s。

## 修复后

连续 **10 次** `inspect`：**10/10** 一致拿到 original 43.5 MiB / HTTP 206，无失败、无降级。

下载结果（`--quality original`，默认路径 `~/Downloads/douyin/<aweme_id>/`）：

| 项 | 值 |
|---|---|
| bytes | 45,562,198 |
| sha256 | `787a5fdbded6245bff6d6a0cfbaaab031673ae19ddbc178e82e39eb7652dbaf4` |
| 分辨率 / codec | 1440×2560 HEVC |
| container bitrate | 14,284,343（≈14.28 Mbps） |
| audio | AAC |
| duration | 25.517279s |

两次独立运行的 sha256 完全一致。作为对照，水印档只有 2,987,248 bytes——**约为原片的 1/15**，这就是静默降级的实际代价。

水印护栏亦经实测验证：在真实 metadata 上人为把 original probe 置为 ConnectTimeout，`--quality original` 报错中止而非返回水印文件。

## 第三条：另一条 0 档 bit_rate 视频（复现）

测试输入：`https://v.douyin.com/-YfeXSbV3Js/`（`aweme_id=7676048935948946715`）

同样是 **0 档 `bit_rate[]` + 纯 SSR** 的形态，用来验证上面的修复不是只对单条视频有效：

- 连续 6 次 `inspect`：**6/6** 一致拿到 original 33.9 MiB / HTTP 206。
- 下载实测 35,539,941 bytes，sha256 `cc0c5acb1ac79d125e7d8efedb48ebb2668fd5494207e80ee713eae36d5dd700`。
- ffprobe：1920×1080 **H.264** 60fps / 容器码率 16,480,385（≈16.48 Mbps）/ 17.251995s / AAC。
- 对照水印档 6,422,925 bytes —— 原片是它的 **5.5 倍**。

注意这条是 **H.264 60fps**，而前一条是 HEVC。原片的 codec 不固定，
**不能假设原片一定是 HEVC**，也不能靠 codec 反推是不是原片。

## 三条视频汇总

| 形态 | provider | 原片 | 回退档 | 倍数 | 原片规格 |
| --- | --- | ---: | ---: | ---: | --- |
| 12 档 bit_rate | `douyin_browser` | 15,864,119 | 6,601,022 | 2.4× | 1080p HEVC 60fps |
| 0 档 bit_rate | `iesdouyin_ssr` | 45,562,198 | 2,987,248 | **15×** | 1440×2560 HEVC |
| 0 档 bit_rate | `iesdouyin_ssr` | 35,539,941 | 6,422,925 | 5.5× | 1080p H.264 60fps |

倍数差异很大（2.4× ~ 15×），**说明「原片比最高转码档大多少」无法预估**，
只能实际探测——这也是不能用体积阈值当判据的原因。

## 结论

首版的核心选择逻辑（original 优先 + 体积对比）是**正确的**，问题全部出在把**瞬时网络失败当成了终局结论**。

超时值本身就是判据的一部分：connect 上限设得比「坏连接挂死的时长」还大时，重试等于没加。

⚠️ 判稳定性**不能只跑一次**。首版之所以带着 ~30% 失败率交付，正是因为验证只跑了顺利的那一次。
