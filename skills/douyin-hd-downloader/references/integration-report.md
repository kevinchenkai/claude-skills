三条公开视频的端到端实测：候选枚举 → 探测 → 选择 → 下载 → ffprobe。
既是首版链路可工作的证据，也是修掉三个可靠性缺陷的过程记录。

> **这些数字不能写进单元测试。** CDN、档位、大小和编码都会随平台重新转码而变化。
> 它们是「当时实测到什么」的快照，不是常量。

# 第二部分：视频 B —— 0 档 bit_rate，暴露三个缺陷

## 修复前：同一条链接，5 次跑出 3 种结果

| run | 结果 |
| --- | --- |
| 1、3、4 | ✅ original 43.5 MiB |
| 2 | ❌ 退出：`WAF challenge` |
| 5 | ⚠️ original `FAIL:ConnectTimeout` → 静默降级到 2.8 MiB 水印档，**exit 0** |

三个根因，均经实测证实（非阅读推测）：

1. **`verifyCenter` 被误判成 WAF**。抓 6 次页面对比：该字符串在 **6/6** 页面都出现，
   包括 5 次成功解析的页面。它是常驻 JS SDK 名，不是风控标记。
   误报把排查方向引向 cookie / 代理，而真实需求只是重试。
2. **完全没有重试**。SSR 单次成功率 4/6；≤3 次独立尝试成功率 **6/6**
   （实测每次所需尝试数：`[2,1,1,1,1,2]`）。
3. **一次 ConnectTimeout 就判原片无效**。10.4s 超时后紧接着重探同一 URL，
   两次均为 206 / 45,562,198 bytes。43.5 MiB 原片被换成 2.8 MiB 水印视频，且 exit 0、不报错。

## 加了重试还不够：连接超时的真实成因

「重试 3 次」的第一版修复**仍然失败** —— 实测出现**连续 3 次** ConnectTimeout，
失败不是独立均匀分布的。

排查中两个假设被实测证伪，记录如下以免后人重走：

- ❌ **假设「某些 CDN IP 挂了」** → `www.douyin.com` 解析到 18 个 IP，**18/18 TCP 连接全部 0.0s 成功**。不是死 IP。
- ❌ **假设「触发了限流」** → 暂停 20s 后立刻重试**仍然失败**，失败率与请求节奏无关。不是限流。
- ✅ **真实成因**：到部分边缘节点的路由不稳定，单次成功率约 50%、相互独立。
  关键观测是**健康连接 ~0.3s，坏连接固定挂满 10.2s** —— 而客户端 connect 上限恰好也设成 10s，
  于是**一个坏边缘就能吃掉整个重试预算**。

修法不是无脑加重试次数，而是**压低 connect 超时 + 提高尝试次数**
（`CONNECT_TIMEOUT_SECONDS = 3.5`，probe attempts 6）：坏边缘快速失败、立刻换一个。
验证 5/5 成功，最坏 4.3s。

> 🔴 **超时值本身就是判据的一部分**：connect 上限设得比「坏连接挂死的时长」还大时，
> 重试等于没加。

## 修复后

连续 **10 次** `inspect`：**10/10** 一致拿到 original 43.5 MiB / HTTP 206，无失败、无降级。

下载结果（`--quality original`，默认落 `~/Downloads/douyin/<aweme_id>/`）：

| 项 | 值 |
| --- | --- |
| bytes | 45,562,198 |
| sha256 | `787a5fdbded6245bff6d6a0cfbaaab031673ae19ddbc178e82e39eb7652dbaf4` |
| 分辨率 / codec | 1440×2560 HEVC |
| container bitrate | 14,284,343（≈14.28 Mbps） |
| audio | AAC |
| duration | 25.517279s |

两次独立运行 sha256 完全一致。作为对照，水印档只有 2,987,248 bytes ——
**约为原片的 1/15**，这就是静默降级的实际代价。

水印护栏亦经实测验证：在真实 metadata 上人为把 original probe 置为 ConnectTimeout，
`--quality original` **报错中止**而非返回水印文件。

# 第三部分：视频 C —— 换一条视频复现

同样是 **0 档 `bit_rate[]` + 纯 SSR**，用来验证修复不是只对单条视频有效：

- 连续 6 次 `inspect`：**6/6** 一致拿到 original 33.9 MiB / HTTP 206
- 下载 35,539,941 bytes，sha256 `cc0c5acb1ac79d125e7d8efedb48ebb2668fd5494207e80ee713eae36d5dd700`
- ffprobe：1920×1080 **H.264 60fps** / 容器码率 16,480,385（≈16.48 Mbps）/ 17.251995s / AAC
- 对照水印档 6,422,925 bytes —— 原片是它的 **5.5 倍**

注意这条是 **H.264**，而视频 B 是 HEVC —— 这是「原片 codec 不固定」的直接证据。

# 结论

首版的**核心选择逻辑是正确的**（original 优先 + 体积对比），
问题全部出在把**瞬时网络失败当成了终局结论**。

三条留给后来者的判据：

1. ⚠️ **判稳定性不能只跑一次。** 首版之所以带着 ~30% 失败率交付，
   正是因为验证只跑了顺利的那一次（即第一部分）。改动后至少连续跑 5 次。
2. 🔴 **超时值是判据的一部分。** 见第二部分——上限比坏连接挂死时长还大时，重试形同虚设。
3. 🔴 **负面结果划定边界。** 上面两个被证伪的假设（死 IP、限流）比结论本身更省时间——
   它们能让后来者不必重走。这与 `known_findings.md` 是同一个原则。
